# ChatGPT 界面组件识别经验

更新时间：2026-07-27

这份文档记录如何从 ChatGPT 界面中识别短暂状态。以后增加“网络搜索”、
“技能调用”、“工具执行”等组件时，可以沿用同一套办法。

## 已验证的例子：正在思考

ChatGPT 回答前会显示“正在思考”，文字上有从左向右移动的高光。

高光只是画面效果，macOS 辅助功能接口不会告诉我们高光移动到了哪里。
真正可用的线索是：

```text
线索一：界面上出现准确文字“正在思考”
线索二：界面上同时存在“停止”按钮
```

两个线索合在一起时，AgentStateBridge 输出：

```text
reasoning
```

只看“正在思考”不够安全，因为聊天记录里也可能出现这几个字。只看“停止”按钮
又只能知道 Agent 正在回答，无法分辨是在思考还是已经开始输出。

这就是本次最重要的经验：一个线索说明“正在做什么”，另一个线索说明
“这个线索现在是否有效”。

## 为什么最初没有识别到

第一次实现要求“正在思考”必须带有 `AXARIALive` 实时区域标记。
这个假设看起来合理，但 ChatGPT 当前版本没有稳定提供这个标记。

因此：

- 屏幕上看得见，不代表辅助功能接口会提供预想中的属性；
- 应当以实际读取结果为准，不能根据网页或动画的实现方式猜测；
- 可选属性可以作为辅助证据，不应在没有验证前成为必要条件。

## 为什么完成状态曾经有延迟

检查器收到了 `AXTitleChanged` 通知，但旧代码只把它显示在记录列表里，没有立即重新读取
界面。回答结束时，如果没有及时收到其他通知，程序就会较晚才发现“停止”按钮已经消失。

现在使用两层检查：

1. 收到相关界面通知后，约 75 毫秒后重新读取；
2. 回答期间每 150 毫秒主动读取一次，作为兜底。

没有回答时，兜底检查放慢到 500 毫秒，减少不必要的开销。

这样既能捕捉短暂的“正在思考”，也能让 `working → completed` 通常在约 150 毫秒内发生。
`completed` 出现后仍最多保留 4 秒，供使用方显示完成效果；这 4 秒不是识别延迟。

## 添加新组件时的步骤

以“网络搜索”为例：

1. 在检查器中临时显示控件名称。
2. 实际触发一次网络搜索，记录出现和消失的控件。
3. 优先寻找准确、稳定的文字、按钮名称、控件类型或 identifier。
4. 再找一个保护条件，例如“停止”按钮存在、回答容器正在变化，或某个工具面板存在。
5. 用两个或更多线索共同判断，不要只依靠一段可能出现在聊天记录中的文字。
6. 把新线索加入 `ControlClassifier`，把组合规则加入 `ActivityInferrer`。
7. 为“应该命中”和“容易误判但不应命中”各写测试。
8. 用真实界面验证出现顺序和持续时间，再更新协议和开发文档。

“技能调用”和“工具执行”也可以使用同样的方法：

```text
组件自己的准确线索
        +
当前回答仍在进行的保护线索
        +
通知触发与短间隔检查
```

## 编写规则时应避免

- 不依赖字体颜色、高光、转圈等纯视觉动画；
- 不固定辅助功能树中的长路径，界面更新后路径容易变化；
- 不对聊天正文做包含匹配；
- 不因为某个属性“理论上应该存在”就把它设为必要条件；
- 不只依赖一种 macOS 通知，因为通知可能缺失、延后或被合并；
- 不把提示词或回答正文写进日志和状态文件。

## 协议扩展建议

增加“网络搜索”或“技能调用”时，先判断使用方是否真的需要独立状态。

如果只需要表现为忙碌，可以继续输出 `working`，并增加可选的细节字段或 evidence。
如果需要独立而稳定的表现，再增加新的状态值。消费者必须继续忽略不认识的字段，
这样后端增加信息时不会破坏旧版程序。

极短的组件状态可能被文件监听合并。`state.json` 适合表达“现在是什么状态”，
已经实现的 Unix socket 则负责把每次变化立即发给消费者。
