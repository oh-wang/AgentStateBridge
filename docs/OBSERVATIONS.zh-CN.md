# ChatGPT 辅助功能信号记录

更新时间：2026-07-27

## 测试环境

```text
应用：ChatGPT
Bundle ID：com.openai.codex
版本：26.721.41059
系统：macOS arm64
```

以下结果来自 Agent State Inspector 的实际运行，不是根据界面截图猜测。

## 已确认的信号

### 输入框

普通任务输入框当前表现为：

```text
role: AXTextArea
title: 随心输入
focused: true（输入框获得焦点时）
```

空输入框的 AX value 可能同样是“随心输入”，因此不能只用“value 是否为空”
来判断用户是否正在输入。当前代码会把 value 与标题和 placeholder 对比；相同时视为空，
不同时才视为用户输入。

界面路径很长，并且可能随版本和窗口结构变化，因此不把路径写进判断规则。

### 工作中的停止按钮

Agent 正在生成回答时，当前界面会出现：

```text
role: AXButton
title: 停止
```

这个信号很清楚，当前版本把它作为 `working` 的主要依据，confidence 为 0.96。

在“停止”按钮存在时，没有找到名称为“发送”的控件。这与“生成期间发送按钮被停止按钮替换”
的界面行为一致。

### 变化通知

观察期间收到了：

- `AXTitleChanged`；
- `AXUIElementDestroyed`；
- `AXFocusedUIElementChanged`。

生成期间大约每秒都会出现标题变化，但目前还不知道是哪一个具体控件发出的，
所以暂时不把“每秒标题变化”直接当成 streaming 信号。

## 已加入的初步判断

| 条件 | 状态 | confidence |
|---|---|---:|
| ChatGPT 未运行 | inactive | 1.00 |
| “停止”按钮存在 | working | 0.96 |
| 输入框中有用户文字 | composing | 0.88 |
| 输入框存在且没有用户文字 | idle | 0.82 |
| 前一次是 working，随后“停止”按钮消失 | completed | 0.90 |

`completed` 保持 4 秒，然后回到根据当前输入框情况判断出的状态。
这 4 秒是最长保持时间。如果期间发现用户开始输入或 Agent 再次开始工作，
会立即进入新状态，不会等满 4 秒。

## 暂缓研究

- 空闲时发送按钮的准确 title；
- 点击提交时是否有独立、稳定的通知；
- 输出正文变化会发出哪一种通知；
- 搜索网页时是否出现独立按钮或状态文字；
- 手动停止与正常完成如何区分；
- 错误和重试控件的名称；
- 多窗口时控件树如何变化。

这些项目只在使用方确实需要更细状态时再继续测试。当前版本统一使用
`working`、`completed` 或 `idle` 即可。

## reasoning 状态

为了让使用方区分思考和生成正文，当前协议提供独立的 `reasoning` 状态。

当前实现接受：

- 文字准确等于实际界面使用的“正在思考”，也兼容“正在思考…”、
  “正在思考中”、“思考中…”或英文 “Thinking…”；
- 同时存在“停止”按钮，表示 ChatGPT 确实正在回答。

只有文字而没有“停止”按钮时，不会触发该状态。实际测试发现，这段文字没有
可靠的 `AXARIALive` 标记，因此当前实现不再依赖该标记。

回答期间每 150 毫秒主动检查一次界面，用来捕捉短暂的“正在思考”，
也用来尽快发现“停止”按钮已经消失。其他时间使用较慢的检查作为兜底。

## 人工验证补充

2026-07-27 的实际对话中已经看到：

- Agent 回复期间显示 `工作中 96%`；
- 用户在输入框中打字时显示 `正在输入 88%`；
- 回答结束后显示 `空闲 82%`。
- 修正后实际顺序为 `工作中 → 刚刚完成 → 空闲`；
- 在新打开的对话窗口中也验证通过。
- 放宽错误的 `AXARIALive` 限制并加入快速检查后，
  `正在思考 → 工作中 → 刚刚完成` 已通过真实界面验证；
- `工作中 → 刚刚完成` 的明显延迟已经消除。

第一次验证时没有来得及看到 `刚刚完成 90%`。检查代码后发现，回答结束时连续到来的
多个 AX 通知可能让第二次扫描提前覆盖 completed。现已改为：completed 在 4 秒内不会被
后续扫描覆盖，并在检查器中保留状态变化记录。
